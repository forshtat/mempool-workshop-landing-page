Alternative Mempools for Frame Transactions

EIP-8141's public mempool says no to almost everything that needs real validation logic. ERC-8421 lets nodes say yes, by pricing abuse with stake and reputation instead of banning whole features.

The canonical mempool is strict on purpose

A Frame Transaction replaces the hard-coded signature check with EVM code. That code runs in the validation prefix, and a node must run it before it may relay the transaction. Nobody pays the node for that work.

If the prefix reads state that anyone can change, one cheap write can invalidate thousands of pending transactions at once. That is the mass invalidation attack, and it is what every rule below exists to stop.

We can do more outside the protocol

Mempool rules need no consensus change. The canonical mempool avoids risk at any cost. An Alternative Mempool trades a little of that safety for features, and covers the risk with three tools.

Stake makes identities cost something

Creating an on-chain entity is free. A stake of roughly USD 1000 with a one-day unstake delay gives it a price. The stake is never slashed. The lock-up is the cost.

Reputation lets trust build up

Each node counts how often an entity's transactions are seen and how often they are included. Entities that cause invalidations get throttled, then banned.

Tracing sees what validation actually did

Nodes trace the simulation and check which storage slots were touched. Slots keyed by the sender's address count as the sender's own.

How an entity earns and loses its standing

A node counts how often it has seen an entity's transactions, and how many of them were included in a block. Good behaviour builds standing. When the gap grows, the entity is limited, then removed.

What you can build with that freedom

Privacy protocols

Some withdrawals need far more than 100k gas to verify. A sender can spend 250k unstaked, or 2.5M with stake, and a keyed nonce per user keeps their transactions independent.

Stateful paymasters

Token paymasters are the best-known case: ERC-20 balances and allowances live in arbitrary storage. More broadly, a paymaster can keep its own state, such as quotas, subscriptions or credits. A pre_verify frame lets it collect or update that state before it commits to pay.

Keystore contracts

Credentials live in storage outside the sender account. Slots associated with the sender are readable.

Quantum cryptography

Post-quantum signatures run in plain EVM code, without precompiles. That costs gas well beyond the canonical limit.

Zero-knowledge proofs

Verifying a proof in validation needs a higher budget. A minimal check fits the unstaked 250k, and stake buys more.

Rules of your own

Trust a contract you audited. Swap hot Solidity for a Rust binary. Track reputation differently. It is your mempool.

Backwards compatibility with the ERC-4337 ecosystem

ERC-8421 keeps what ERC-7562 made possible. The contract logic carries over. The interfaces around it change.

Stake, reputationSame ideas. Stake sits in a Staking Registry and is never slashed. Reputation is tracked per entity address and per mempool.

ERC-8421 introduces no consensus change, requires no change to EIP-8141 or the FOCIL rules of EIP-7805, and does not modify ERC-4337 or ERC-7562.

Modular mempools, one open submission market

A mempool is an app, not a protocol constant. Nobody has to agree on one set of rules: each mempool bundles its own validation rules, and nodes opt into the ones they want to serve.

Reaching the mempool is only the first step

The Alternative Mempool rules partially satisfy the FOCIL profile for Frame Transactions. A transaction that complies may get better censorship resistance in an adversarial environment. FOCIL forces inclusion unless the transaction is invalid, so attesters need to know whether it is valid.

A mempool sidecar you can run today

The mempool sidecar is a TypeScript node for EIP-8141. It exposes eth_sendFrameTransaction, validates and simulates transactions against an execution client, relays them on-chain, and gossips them to other sidecars over libp2p.

There is no EntryPoint and no eth_sendUserOperation. It needs an execution client that implements EIP-8141. Today that is the eip8141-tracer branch of ethrex.
